# URI와 원자화 규칙

## 기본 원칙

1. 새 번호를 만들지 않는다. 나라에서 이미 쓰는 번호를 그대로 쓴다.
2. 형식은 `https://yeodh10.github.io/jeungmi-geokg/id/{객체종류}/{공식번호}`이다.
3. 한 번 붙인 URI는 바꾸지 않는다. 객체가 사라져도 URI는 남기고 "폐지" 상태로 표시한다.
4. 공식 번호가 없는 객체만 예외 규칙을 두고, 그 규칙을 이 문서에 적는다.
5. 모양(Geometry)은 객체(Feature)와 따로 URI를 갖는다: `{객체 URI}/geometry`

아래 예시에서 `{base}`는 `https://yeodh10.github.io/jeungmi-geokg/id`를 줄인 것이다.

## 원자화 규칙 (2026-11-05 정리)

원천 공공데이터는 표(행과 열)나 도면(레이어와 도형)으로 온다. 그래프에는 이것을 실물 단위의 객체와 관계로 쪼개 넣는다. 아래는 지금까지 객체 종류마다 정한 규칙(이 문서의 아래 절)에서 공통으로 쓰는 원칙이다.

1. **객체는 원천 행이 아니라 실물 하나다.**
   - 기준이 되는 공식 번호 하나가 객체 하나다. 예: 건물관리번호 하나가 건물 하나다.
   - 원천 행과 실물이 1대1이 아니면 실물 쪽을 따른다.
     - GIS 폴리곤 하나에 건물관리번호가 여럿이면 건물을 여럿 만들고 같은 모양을 함께 쓴다.
     - GIS 자료에 같은 건물이 두 행으로 들어 있으면 하나로 합친다.
   - 실물이 같은지 판단할 근거가 없으면 합치지 않는다. 예: 이름이 다른 상호 두 행은 그대로 두 객체로 둔다.
2. **여러 객체가 함께 가리키는 값은 따로 객체로 만들고 관계로 잇는다.**
   - 도로명, 필지, 법정동, 행정동, 기초구역이 여기에 든다. 건물마다 같은 문자열을 되풀이하지 않는다.
   - 대신 `jgk:addressRoad`, `jgk:locatedOn`, `jgk:inLegalDong`, `jgk:within`, `jgk:inBasicZone`으로 그 객체를 가리킨다.
   - 그래야 "이 길을 주소로 쓰는 건물"처럼 거꾸로 따라가는 질문이 쿼리 하나로 된다.
   - 한 객체에만 붙는 값(층수, 용도, 사용승인일, 높이)은 속성(리터럴)으로 둔다.
3. **관계는 작은 것에서 큰 것으로 건다.**
   - 출입구는 건물에서 `jgk:hasEntrance`로 가리키고, 건물은 필지와 동을, 역과 공공시설은 건물을 가리킨다(`jgk:housedIn`).
   - 도로 구간은 도로를 가리킨다(`jgk:segmentOf`).
   - 대칭인 관계(옆 역 `jgk:adjacentStation`)는 추론기 없이도 보이게 양쪽으로 넣는다.
4. **모양은 객체와 따로 둔다(`{객체 URI}/geometry`).**
   - 모양의 출처가 객체의 출처와 다를 수 있다. 예: 점만 있던 건물에 국가기본도 모양을 붙이는 경우.
   - 모양만 바뀌어도 객체 URI는 그대로다.
   - 공개 보류는 모양 노드의 출처를 보고 모양만 뺄 수 있다.
5. **같은 실물이 여러 자료에 있으면 합치지 않고 잇는다.**
   - 국가기본도 건물, 수치지형도 건물, 주소 미연결 건물은 각자 객체로 두고 잇는다.
   - 잇는 관계는 `jgk:basemapFeature`, `jgk:digitalMapFeature`, `jgk:sameBuildingAs`다.
   - 자료마다 값(모양, 층수, 이름)이 다를 수 있어서 한 객체에 섞지 않는다.
   - `owl:sameAs`는 바깥 번호가 같은 실물을 가리킬 때만 쓴다. 예: 위키데이터의 세 역.
6. **값은 원천에 있는 것만 넣는다.**
   - 그래프에는 원천 값과 사람이 승인한 변경만 들어간다.
   - 지도에서 층수로 어림한 입체 높이는 화면에서만 계산하고 그래프에 넣지 않는다.
   - 원천에 없는 값은 '없는 정보'로 보여 준다.
7. **모든 객체는 출처와 상태를 하나씩 가진다.**
   - 출처는 `dcterms:source`(자료 이름, 기준월은 자료 목록에 있다)로 적는다.
   - 상태는 `jgk:status`(사용, 주소 미연결, 주소 연결됨, 폐지)로 적는다.
   - 지형지물 분류는 국가기본도 분류(`jgk:featureCode`, 수치지도 작성 작업규칙 제9조)를 따른다.
8. **범위는 한 번 정한 규칙으로 자른다.** 증미역 중심 1km 원으로 자른다.
   - GIS 건물은 원에 걸치면 넣는다.
   - 내비게이션용DB 중심점은 원 안에 있어야 넣는다.
   - 역사 건물처럼 어떤 건물이 무엇인지는 짐작하지 않는다. `config/area.yaml`에 공식 번호로 적는다.
9. **객체를 고치지 않고 바꾼 이력을 남긴다.**
   - 원천이 바뀌거나 고시가 나오면 그래프를 바로 고치지 않고 변경 제안을 만든다.
   - 사람이 승인하면 바뀐 트리플마다 변경 기록(`rdf:Statement`)이 남는다(아래 '변경 제안과 변경 기록 규칙').
   - 사라진 객체는 지우지 않고 폐지로 둔다.

## 파이프라인 단계

`python -m src.pipeline`이 원본에서 공개 페이지까지 아래 순서로 다시 만든다. 단계마다 걸린 시간과 핵심 숫자가 `data/processed/pipeline_report.json`에 남는다. 승인 기록(`proposals.json`)은 읽기만 한다.

| 단계 | 하는 일 | 코드 |
|---|---|---|
| 1. 범위 자르기 | 원천 자료를 증미역 반경 1km로 자른다. 위 원자화 규칙 8의 경계 규칙을 쓴다 | `src/ingest/clip_area.py` |
| 2. 객체 쪼개기와 URI | 건물, 출입구, 필지, 도로와 도로 구간, 동, 기초구역, 역, 공공시설로 쪼개고 공식 번호로 URI를 붙인다. 모양을 고르고 속성을 붙인다 | `src/model/build_objects.py`, `src/model/uri.py` |
| 3. 센서와 관측, 상호 | S-DoT 센서와 관측(SOSA), 상가정보 상호를 객체로 만들고 건물이나 필지에 잇는다 | `src/model/build_sensors.py`, `src/model/build_business.py` |
| 4. 그래프 | GeoSPARQL 그래프로 옮기고, 승인된 변경 제안을 변경 기록과 함께 얹는다. 측량 성과 계보(도엽 메타데이터)도 여기서 붙인다 | `src/graph/build_graph.py` |
| 5. 검사 | 예시 SPARQL 쿼리의 답을 확인하고, SHACL 규칙(번호 하나, 상태 하나, 관계 대상의 종류)과 바깥 어휘 정렬을 검사한다 | `src/graph/check_queries.py`, `src/graph/validate.py`, `src/graph/interop.py` |
| 6. 공개 | 공개 보류 출처를 뺀 공개 뷰로 URI 페이지와 지도 앱 자료를 만든다 | `src/graph/publish.py`, `src/graph/appdata.py` |
| 7. 공개 전 검사 | 공개 파일에 보류 자료의 주소, 속성, 출처, 이름과 키가 없는지 보고, 앱 자료의 좌표를 공개 뷰의 모양과 견주고, 상태 수를 원천 수와 승인으로 다시 셈한다 | `src/graph/public_check.py` |

변경은 이 단계 밖에서 들어온다.

- 다음 기준월 원본과 견준 자동 갱신 제안(`src/review/diff_proposals.py`)과 다른 자료와 잇는 제안이 있다.
- 구청 고시에서 LLM으로 뽑은 제안(`src/llm/notice.py`, 입력 가드와 원문 대조를 거친다)도 있다.
- 이것들이 검토 화면에서 승인되면, 다음 파이프라인 실행의 4단계에서 그래프에 얹힌다.

## 상태 값

모든 객체는 상태를 하나 가진다.

| 상태 | 뜻 |
|---|---|
| 사용 | 원천 데이터에 있고 공식 번호로 식별된다 |
| 주소 미연결 | 건물 모양은 있지만 건물관리번호를 찾지 못했다 (`building-gis`만 해당) |
| 주소 연결됨 | 예전에 주소 미연결이던 건물이 나중에 건물관리번호와 이어졌다 |
| 폐지 | 원천 데이터에서 사라졌다. URI는 남긴다 |

## 건물 규칙 (2026-10-28 확정)

건물 URI는 두 갈래로 나뉜다. 건물관리번호가 있으면 그것을 쓰고, 없을 때만 GIS건물통합정보 자체 고유번호를 쓴다.

### 1. 주소가 연결된 건물: `building/{건물관리번호}`

- 내비게이션용DB의 건물관리번호마다 건물 객체를 하나 만든다. 상태는 `사용`.
- 모양은 건물중심점을 포함하는 GIS건물통합정보 폴리곤으로 정한다.
  - 폴리곤 하나에 건물관리번호가 하나만 들어 있으면 그 폴리곤을 쓴다 (반경 안 1,751개).
  - 폴리곤 하나에 건물관리번호가 여러 개 들어 있으면(반경 안 39개 폴리곤, 한 폴리곤에 2 ~ 5개) 각 건물 객체가 같은 폴리곤을 모양으로 가진다. 모양 노드는 건물마다 따로 두고, 어느 폴리곤에서 왔는지 A1 번호를 모양에 적어 둔다.
  - 어느 폴리곤에도 들어가지 않는 건물중심점(반경 안 324개)은 건물중심점 자체를 점 모양으로 쓴다. 국가기본도 건물 모양을 붙이는 제안(src/review/basemap_proposals.py)을 승인하면 같은 모양 노드(`{건물 URI}/geometry`)의 값이 그 모양으로 바뀌고, 모양 출처를 국가기본도로 적는다. URI는 그대로다.
- 건물 상세 속성은 연결된 폴리곤의 대장 속성(A8 ~ A27)을 쓴다.

### 2. 주소가 연결되지 않은 건물: `building-gis/{GIS건물통합식별번호}`

- 건물관리번호를 가진 건물중심점이 하나도 들어 있지 않은 GIS 건물 폴리곤에 붙인다 (반경 안 628개). 이 가운데 34개는 건물중심점이 원 밖이어서 범위 자르기에서 빠진 경계 건물(새 건물 36동)의 모양이었다. 원천 그래프(9월분 원본으로 만든 바탕)는 그대로 두고 자동 갱신으로 새 건물을 만들어 이었다 (아래 규칙 4, docs/decisions.md 2026-11-03).
- 번호는 GIS건물통합정보 A1(28자리)을 그대로 쓴다. A0는 고유하지 않아 쓰지 않는다.
- 상태는 `주소 미연결`.
- 모양은 그 폴리곤이다. 상세 속성도 같은 폴리곤의 대장 속성을 쓴다.
- 형식: `{base}/building-gis/{A1 28자리}`

### 3. A1 번호가 겹칠 때

GIS건물통합정보에는 같은 A1이 두 행 이상인 경우가 있다(서울 전체 405개 번호, 반경 안 1개).

- A0만 다르고 나머지 속성과 모양이 모두 같으면 같은 건물이 두 번 들어간 것으로 보고 하나로 합친다. 반경 안의 1건(염창동 242-40)이 이 경우다.
- 속성이나 모양이 다르면 URI를 만들지 않고 검토 목록에 올린다. 사람이 확인한 뒤 규칙을 이 문서에 더한다. 반경 안에는 현재 이런 경우가 없다.

### 4. 나중에 주소가 연결되면

- 데이터를 갱신하다가 `building-gis` 건물에 건물관리번호가 생기면 새 `building/{건물관리번호}` 객체를 만든다.
- 기존 `building-gis` URI는 지우거나 바꾸지 않는다. 상태를 `주소 연결됨`으로 바꾸고 `jgk:sameBuildingAs`로 새 URI와 잇는다.
- `owl:sameAs`는 쓰지 않는다. 이어진 두 객체는 출처 자료가 달라서 모양, 용도, 이름, 층수가 다른 쌍이 있다. 또 `owl:sameAs`로 추론하면 한 객체에 건물관리번호와 GIS 번호가 함께 생겨 '번호는 정확히 하나' 규칙과 부딪힌다. `owl:sameAs`는 외부 번호가 같은 실물을 가리킬 때만 쓴다(예: 위키데이터의 증미역). 2026-11-02 전에 승인한 제안은 `owl:sameAs`로 이었다. 2026-11-03에 승인 기록은 그대로 두고, 옮기는 제안(`fix-same-building-*`, `src/review/same_building_migration.py`)을 만들어 모두 `jgk:sameBuildingAs`로 바꿨다. 옛 그래프도 검사할 수 있도록 SHACL 규칙은 두 관계를 모두 본다.

### 5. 확인할 것

- A1이 데이터 갱신 뒤에도 같은 건물에 그대로 유지되는지는 아직 확인하지 않았다. 다음 날짜 파일을 받으면 반경 안 A1 목록을 비교해 결과를 여기에 적는다.

## 필지 규칙 (2026-10-28 확정)

- `parcel/{PNU}`. PNU는 19자리.
- 모양으로는 연속지적도(참조용 도면)에서 PNU가 같은 폴리곤을 `{필지 URI}/geometry`에 붙인다(2026-11-03, 1,760개 중 1,718개). 모양 노드의 출처는 연속지적도다.
- 연속지적도에 없는 PNU 42개는 모두 GIS건물통합정보 A2에서만 나온 번호다. 그 위 건물의 대표점이 모두 지금 지적상 다른 필지 안에 있어서, 분할이나 합병 뒤 GIS 쪽 PNU가 갱신되지 않은 것으로 본다. 목록은 `review_parcel_no_boundary.csv`에 있다.
- 분할, 합병, 지적재조사로 PNU가 없어지면 옛 `parcel/{PNU}` URI는 지우지 않고 상태를 폐지로 바꾸며, 새 PNU는 새 객체로 만든다(자동 갱신의 retire, create 제안). 옛 필지와 새 필지를 잇는 관계(예: `dcterms:isReplacedBy`)는 아직 넣지 않았다. 행정구역 개편으로 법정동코드가 바뀌어 PNU가 바뀌는 경우도 같다.
- 필지 객체는 GIS건물통합정보 A2와 건축물대장 총괄표제부에 나오는 PNU로 만든다.
- 건축물대장 총괄표제부의 단지 정보는 이 필지 객체에 붙인다.

## 출입구 규칙 (2026-10-29 확정)

전자지도 출입구 레이어에는 출입구일련번호(ENT_MAN_NO, 시군구 안에서 고유)가 있지만, 아래 URI는 이미 GitHub Pages로 공개했으므로 바꾸지 않는다.
전자지도 번호는 공개 보류 자료라 속성으로 넣지 않았다.

- 건물 출입구
  - 주출입구: 건물마다 하나라서 건물 번호에 붙인다. `entrance/{건물관리번호}-main`
  - 보조출입구: 내비게이션용DB의 PK가 (시군구코드, 출입구일련번호)라서 그대로 쓴다. `entrance/{시군구코드}-{출입구일련번호}`
  - 도로명주소 전자지도의 출입구 레이어에 고유 번호가 있으면 그것으로 바꾸되, 바꾸기 전에 붙인 URI가 공개된 적이 없을 때만 바꾼다.

## 도로 규칙 (2026-10-29 확정)

- 도로 하나는 도로명 하나에 대응한다. `road/{도로명코드 12자리}`. 건물 도로명주소의 도로를 `jgk:addressRoad`로 가리킨다.
- 도로 구간은 `road-segment/{시군구코드}-{도로구간 일련번호}`. 일련번호가 시군구 안에서만 고유해서 보조출입구처럼 시군구코드를 앞에 붙인다. 숫자 앞에 0을 채우지 않는다.
- 출입구는 `jgk:facesRoad`로 자기 주소 도로명과 같은 도로 구간 가운데 가장 가까운 것(60m 안)에 잇는다.

## 역 규칙 (2026-10-29 확정)

- `station/{역사 건물의 건물관리번호}`. 역은 역사 건물과 다른 객체지만 번호는 역사 건물의 건물관리번호를 그대로 쓴다.
- 예: 증미역 `{base}/station/1150010200106660040000001`
- 역은 `jgk:housedIn`으로 역사 건물(`building/{같은 번호}`)과 잇는다. 모양은 역사 건물의 모양을 복사해 따로 둔다.
- 어떤 건물이 역사인지는 추측하지 않고 `config/area.yaml`의 `stations`에 건물관리번호로 적는다.
- 2026-11-04부터 범위 안의 역은 셋이다: 증미역(중심), 가양역 `{base}/station/1150010400100140061000001`, 등촌역 `{base}/station/1150010200106660094000001`. 옆 역 관계는 `jgk:adjacentStation`이고, 근거는 위키데이터 인접역(P197)이다.

## 공공시설 규칙 (2026-10-29 확정)

- `public-facility/{행정표준코드 기관코드}`. 기관코드는 행정안전부 행정표준코드관리시스템이 매기는 7자리 번호다.
- 같은 건물에 기관이 여럿 있어도 기관마다 번호가 달라 겹치지 않는다.
- 행정표준코드의 폐지구분(현존, 폐지)을 그대로 상태(`사용`, `폐지`)로 옮긴다.
- 공공시설은 `jgk:housedIn`으로 들어 있는 건물과 잇는다.
- 기관코드가 없는 시설(예: 우편취급국)은 새 번호를 만들지 않는다. URI를 붙이지 않고 검토 목록에 남긴다.
- 확인 예: code.go.kr에서 기관코드를 검색하면 번호와 전체기관명이 나오고, "우편취급국"으로 검색하면 결과가 없다 (2026-10-29).

### 민원행정기관 이름을 기관코드에 맞추는 규칙

현존 기관 중 전체기관명에 시도 이름이 들어 있는 기관만 본다. 아래 순서로 보고, 후보가 나온 단계에서 멈춘다. 후보가 정확히 하나일 때만 URI를 붙인다.

1. 이름 일치: 최하위기관명이 같다. (같은 이름의 소방서가 여러 시도에 있어도 시도 이름으로 서울만 남긴다)
2. 동 이름 일치: "OO동주민센터"는 같은 시군구의 "OO동"이다.
3. 이름 끝부분 일치: 최하위기관명(4자 이상)이 민원행정기관 쪽 이름의 끝부분과 같다. (시도와 구 이름을 앞에 붙인 지구대 이름)

규칙으로 맞추지 못한 시설은 `data/processed/review_public_facility.csv`에 남기고 사람이 정한다.

2026-10-29 결과: 반경 안 26곳 중 23곳에 기관코드를 붙였다(이름 일치 18, 동 이름 일치 3, 이름 끝부분 일치 2). 남은 3곳:

| 시설 | 곳 수 | 이유 |
|---|---|---|
| 우편취급국 | 2 | 우편취급국은 기관코드가 없다 |
| 고용복지플러스센터 | 1 | 이름이 달라 규칙으로 맞추지 못했다. 사람이 볼 후보가 하나 있다 |

### 공공시설이 들어 있는 건물 (housedIn)

- 민원행정기관의 도로명주소(시군구코드 + 도로명코드, 지하여부, 본번, 부번)가 같은 건물을 찾는다.
- 한 주소에 건물이 여럿이면(단지) 시설 위치를 품은 건물만 남긴다. 품은 건물이 없으면 그 주소의 건물을 모두 잇는다.
- 2026-10-29 결과: 23곳 중 22곳이 건물과 이어졌다. 나머지 1곳은 같은 주소의 건물이 반경 안 자료에 없어 잇지 못했다.

## 변경 제안과 변경 기록 규칙 (2026-11-02 확정)

- 제안: `proposal/{제안 id}`. 나라에서 붙인 번호가 없는 자체 기록이라 제안 id를 그대로 쓴다. id에는 영문, 숫자, `.`, `_`, `:`, `-`만 쓴다.
- 변경 기록: 그래프에서 실제로 바뀐 트리플 하나마다 `{제안 URI}/change/...` 노드(`rdf:Statement`)가 남는다.

| URI | 뜻 |
|---|---|
| `/change/0` | 첫 승인이 대상 객체에 제안 연결(`prov:wasInfluencedBy`)을 넣은 사건 |
| `/change/{번호}` | 첫 승인의 변경. 번호는 제안의 changes 안 자리(1부터) |
| `/change/{회차}-{번호}` | 정정으로 철회한 뒤 다시 승인한 변경. 회차는 2부터다. 예: `/change/2-1` |
| `/change/undo-{회차}-{번호}` | 승인을 철회할 때 되돌린 변경. 번호 0은 제안 연결을 뺀 사건이다. 예: `/change/undo-1-1` |

## 센서와 관측 규칙 (2026-10-30 확정)

- 센서: `sensor/{모델 시리얼}`. 서울시가 설치 위치정보와 관측 파일 양쪽에 같은 시리얼을 쓴다. 센서를 바꾸면 시리얼이 바뀌고 설치 위치정보에 '변경 전 시리얼'이 남으므로, 바뀐 센서는 새 URI를 받고 옛 URI는 폐지 상태로 둔다.
- 관측: `observation/{시리얼}-{측정 시각 YYYYMMDDHHMM}-{항목}`. 관측에는 나라에서 붙인 번호가 없어서, 공식 번호(시리얼)와 원본에 있는 값(측정 시각, 항목)만 이어 만든다. 한 센서는 한 시각에 한 항목을 한 번만 재므로 겹치지 않는다(만들 때 검사한다). 예: `observation/V02Q1940104-202610120007-noise`
- 항목 이름: temperature(기온), humidity(습도), noise(소음), illuminance(조도), uv(자외선). 어휘의 `jgk:temperature` 같은 관측 항목(sosa:ObservableProperty)과 같은 이름이다.

## 상호 규칙 (2026-11-03 확정)

- URI: `business/{상가업소번호}`. 예: `{base}/business/MA0101202310A0001390`. 상가정보의 번호를 그대로 쓴다. 숫자와 영문 대문자 20자리다.
- 원천 행 하나가 객체 하나다. 같은 가게가 이름이 달라 두 행으로 나와도(올리브영증미역점, 씨제이올리브영증미역점) 합치지 않고 둘 다 객체로 둔다. 합치기는 화면 목록에서만 한다.
- 다음 분기 자료에서 번호가 없어지면 URI는 남기고 폐지 상태로 둔다(다른 객체와 같다).
- 건물 잇기(`jgk:inBuilding`): 상가정보의 건물관리번호와 같은 우리 건물이 있으면 그 건물에 잇는다. 없으면 PNU가 같은 건물이 하나뿐일 때 그 건물에 잇는다. 둘 다 안 되면 PNU 필지에만 `jgk:onParcel`로 잇는다. 어떻게 이었는지 `jgk:linkedBy`에 '건물관리번호', 'PNU', '필지만'으로 적는다. 주소 미연결 건물(`building-gis`)과도 PNU로 이어질 수 있다.
- 상가정보에 없어 사람이 직접 넣은 장소(`config/places_extra.yaml`)는 공식 번호가 없어 URI를 만들지 않는다. 새 번호를 지어내지 않기 위해서다. 화면 자료에만 출처와 함께 넣는다.
